# DevSupport AI 面试准备

## 一、项目介绍

### 1. 自我介绍中的简洁版本

我设计过一个面向 API 开放平台的多 Agent 智能客服系统，技术上基于 Python、FastAPI、LangGraph 和通义千问实现。系统以 LangGraph 的 DAG 工作流为核心，串联意图路由、混合 RAG、业务工具诊断、会话记忆和安全兜底，能够完成 API 问题的自动分析与处理。项目中我重点做了检索和链路性能优化，将冷启动 P95 从约 48.6 秒优化到 6.8 秒。

### 2. 面试官追问项目时的介绍版本

这是一个面向 API 开放平台的多 Agent 智能客服系统，目标是处理开发者在 API 调用中的报错、限流、文档使用和账单等问题。

从架构上看，前端通过 SSE 调用 FastAPI 服务，后端以 LangGraph StateGraph 组织 DAG 工作流：先加载会话上下文，完成意图识别和实体抽取，再按问题类型路由到文档 RAG、API 诊断或账单解释等 subagent 角色；之后通过结果汇总、工单创建和安全审查等后处理节点完成兜底和最终输出。

最主要的能力包括两部分：一是 RAG，采用 Milvus 向量检索和 BM25 关键词检索双路召回，经过 RRF、Rerank 和上下文压缩后生成带引用回答；二是工具诊断，通过调用日志、API Key、套餐和账单等工具获取真实证据，再由模型组织为诊断结论和修复步骤。

技术上还加入了 Redis 记忆与缓存、敏感信息三层脱敏、链路追踪和按租户的 Token 统计。性能上，我通过模型分层、错误码热路径、路由缓存、语义缓存和并行执行，将冷启动 P95 从约 48.6 秒降到 6.8 秒。

## 二、面试口径提醒

- 严格按照“有 LLM 参与专业任务决策或生成”的口径，项目中主要有 4 个 LLM 角色：IntentRouter、DocRAG、APIDiagnostic 和 Billing。
- Supervisor 是基于 LangGraph 的确定性编排器，不是自主 Agent。
- `ticket_node` 和 `security_node` 主要是规则节点；`summarize_node` 是包含一次 LLM 总结调用的后处理节点，不建议单独称为 Agent。
- 多个专业角色在 `specialists_node` 内通过 `asyncio.gather` 并行执行，结果由 `summarize_node` 汇总。
- 当前图没有使用 LangGraph Checkpoint；对话历史和实体记忆在 Redis 中维护，Trace 和业务数据在图外持久化。
- 当前 SSE 主要是结果完成后的分块推送，属于伪流式展示，不是完整的 LLM token 级流式链路。
- 简历中的性能数字要确认基线和计算方式：48.58 / 6.83 约等于 7.1 倍；0.74 / 0.010 约等于 74 倍。
